## 2 · CPU 与 GPU：职责、吞吐量与等待

上一节区分了顶点、图元、样本和片元。它们也提示了并行的来源：对许多顶点执行相同的变换，对许多片元执行相同的材质程序。并行改变的是任务的组织方式，前面推导的坐标、覆盖和颜色关系仍需成立。

在常见实时系统中，CPU 组织应用状态、更新场景、准备资源并提交绘制命令；GPU 执行大量顶点和片元工作，以及图元装配、光栅化、深度与混合等阶段。具体分工可随系统变化，不能把 CPU 理解为只能做串行工作，也不能认为 GPU 擅长任何类型的程序。

| 阶段 | 主要输入与结果 | 需要保留的区别 |
| --- | --- | --- |
| CPU 准备与提交 | 场景、资源、绘制命令 | 提交命令不等于立即取得结果 |
| 顶点着色 | 顶点属性 → 裁剪空间位置与输出属性 | 顶点程序不直接输出片元 |
| 装配、裁剪、光栅化 | 图元 → 覆盖样本与片元候选 | 这是顶点与片元阶段之间的过程 |
| 片元与帧缓冲操作 | 片元属性 → 候选颜色及最终写入 | 丢弃、深度测试等仍可能阻止写入像素 |

从 CPU 软件管线、固定功能图形加速，到可编程着色阶段，关键变化是可并行处理的工作及其可编程范围。基础篇以这种职责关系理解硬件，不把某一代产品的核心数和时钟频率当成长期有效的性能公式。

### 用一个明确模型观察吞吐量

设有一批互不依赖的任务，第 i 个任务需要 $c_i$ 次相同循环。构造一台有 L 个通道的示意机器：同组任务共用循环步，已经完成的通道暂时空闲；一组结束后再运行下一组。它的计算时间为

$$
T_{\rm compute}=\sum_g\max_{i\in g}c_i,\qquad
W=\sum_i c_i,\qquad
\eta=\frac{W}{L T_{\rm compute}}.
$$

W 是有效工作，η 是此模型的通道利用率。增加通道不一定使每条通道都有效：任务数可能不够，最后一组可能不满，同组任务的循环长度也可能不同。

手算 L=4、迭代数 (1,8,1,8,1,8,1,8)：原顺序两组各需要 8 步，总计 16 步。按长度分为 (1,1,1,1) 和 (8,8,8,8)，总计 9 步；两种安排的有效工作均为 36。若每个任务只有一步，只有两个任务，却要花三个周期启动并行工作，则“启动 3＋计算 1”反而大于标量参考的 2。

### 模型说明了什么，又省略了什么？

实际 GPU 会让多个线程组驻留、调度并交叠执行，并非只运行图中的一个组。以 NVIDIA 的 SIMT 为例，同一个 warp 内的不同执行路径可能导致通道暂时不活跃；现代硬件还有更细的调度机制。[官方编程指南](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html)给出了具体约定。本图用可变循环长度解释通道闲置，未纳入实际指令延迟、缓存和带宽。

吞吐量指单位时间完成多少工作，延迟指一项工作多久完成。为提高吞吐量，系统通常会安排足够多的独立工作；但内存访问、同步与数据依赖仍可能限制收益。把循环长度相近的任务放在一起，也可能破坏原来的内存访问连续性，不能只凭图中的 η 决定实际优化。

CPU 与 GPU 之间还可能有提交、数据传输和结果回读的代价。共享物理内存不意味着同步免费；每提交一个遮挡查询就立刻等待结果，可能抵消[第 06 章](?chapter=depth)节省的绘制工作。优化应比较端到端时间与正确结果，而不只比较某段内核或数值模型。

### 数据的位置也是计算的一部分

并行硬件通常具有寄存器、片上存储与更大容量的设备内存。寄存器保存线程的局部工作，片上共享存储可供一组任务合作，缓存尝试复用邻近或近期访问，设备内存容纳主要数据。容量、带宽和访问延迟不同；“共享”指访问范围，不代表任意线程之间无需同步。

以邻域滤波为例，相邻输出重复读取重叠区域。若能复用输入块，可减少重复读；但搬运和同步也有代价。访问连续地址通常更容易合并事务，散乱地址则可能增加实际读取量。能驻留的工作还受寄存器和片上容量限制，所以减少算术次数不一定降低端到端时间。这里建立存储层次与数据局部性的概念，不展开设备 API 或内核实现；具体机制依赖架构。
